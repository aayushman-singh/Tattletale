# Codex review — Phase 2 verification

_Findings only; model gpt-5.5 xhigh._

---

**Findings**

High: `correlation.ts` complete-linkage guard is too weak. It says “every cross-pair must clear `EDGE_FLOOR`”, not `MERGE_THRESHOLD`. That means A-B and B-C can merge if A-C is only `0.35`, even though `0.35` is explicitly just “not graph noise”, not merge strength. This still permits transitive over-merge through merely flaggable weak links. Complete-linkage for identity merge should require every cross-pair to satisfy the merge criterion, or a separate named cluster-consistency threshold with a defensible meaning.

Medium: `correlation.test.ts` does not actually exercise the transitive blocker described in its comment. In the provided A/B/C fixture, B-C is not strong, so the test only proves “unrelated C does not merge directly.” It does not prove “A-B strong, B-C strong, A-C weak prevents A/B/C collapse.” This leaves the prior blocker under-tested.

Medium: `verifySeal()` accepts any block without checking `algorithm`, `signedField`, `mode`, or `keyId`. A malformed or semantically wrong block can verify if the bytes/signature match. That is a determinism/custody semantics hole: verification should reject blocks whose declared scheme is not exactly the scheme being verified.

Medium: `sealRootHash(rootHash, signingKey)` always emits `mode: "demo-ephemeral"`, even when a caller supplies a stable/pinned key. That makes the API unable to truthfully represent non-ephemeral sealing despite the type advertising `"hsm"`. Either remove `"hsm"` from the type for Phase 2, or make mode an explicit parameter that cannot silently lie.

Medium: `scorePair()` allows one-post pairs to merge. The coverage gate halves behavioral weights at one post, but identical handle/name/bio plus one matching post can still clear `0.55`. If the stated fix is “sparse data can’t false-merge,” this is only partially resolved. Zero posts are blocked; thin evidence is still merge-capable.

Low: `report.json` includes the full `correlation`, and `correlation.json` duplicates it as a separately hashed artifact. That is custody-valid, but conceptually noisy: the same analysis is sealed twice through two paths. If the goal is minimal directed relations, either make `report.json` reference the correlation artifact or accept that the report embeds a snapshot and the artifact is the graph export.

Low: frontend `selectedEdge = edges[selected]` can point at the wrong edge if a new `correlation` prop arrives with a different edge order. In this static demo it probably never happens, but the component is less self-contained than it looks. Reset selection on correlation change or store an edge id.

Low: labels still say `confidence` in `GoldenCrossMatch` and `deriveMatches()`. The UI may not surface “forensic confidence,” but the type/data model still encodes confidence terminology. That is a naming smell after explicitly moving to heuristic scores/bands.

Prior blockers: PDF root claim is genuinely fixed. Demo-ephemeral seal plus optional key pinning is mostly fixed, with the API/mode issue above. “Forensic confidence” is fixed in user-facing correlation language, but legacy `confidence` remains. Zero-post false merge is fixed; sparse-data false merge is not fully fixed. Complete-linkage is not genuinely fixed because it uses `EDGE_FLOOR`, and the test misses the intended case.

VERDICT: NO-GO for a hiring manager, and REMAINING: complete-linkage threshold bug, incomplete sparse-data gate, weak transitive-overmerge test, seal verification metadata validation, misleading `mode` API, lingering `confidence` naming.
